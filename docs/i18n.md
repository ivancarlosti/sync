# Internationalisation

Seven catalogs ship in `web/src/i18n/locales/`:

| Code | Language | Direction | Notes |
|---|---|---|---|
| `en-US` | English | LTR | reference catalog, `fallbackLocale` |
| `pt-BR` | Português (Brasil) | LTR | |
| `es-MX` | Español (México) | LTR | |
| `fr-FR` | Français | LTR | |
| `h-CN` | 中文（简体） | LTR | the code follows the specification; `zh`, `zh-CN`, `zh-Hans`, `zh-TW`… are aliases for browser detection |
| `hi-IN` | हिन्दी | LTR | |
| `ar-SA` | العربية | **RTL** | mirrors the whole document |

All seven have exactly the same key set: **513 keys**, checked by
`web/scripts/check-i18n.mjs` (part of `npm run typecheck`) and, for the keys the
setup guide renders, by `internal/services/i18n_test.go` (`go test ./...`).

## 1. Structure

`web/src/i18n/index.ts` builds the composer:

```ts
createI18n({
  legacy: false,          // Composition API only: useI18n(), never this.$t
  globalInjection: true,
  locale: 'en-US',
  fallbackLocale: 'en-US',
  flatJson: true,         // a key that itself contains a dot is looked up literally
  messages: MESSAGES,     // the seven catalogs, typed: LocaleCode = keyof MESSAGES
  missingWarn: true,      // a missing key is a bug worth seeing in the console
  fallbackWarn: false,
});
```

Catalogs are **nested per namespace** (`{"jobs":{"title":"…"}}` → `t('jobs.title')`)
and the namespaces are stable:

`common`, `nav`, `auth`, `status`, `validation`, `dashboard`, `accounts`,
`browser`, `jobs`, `runs`, `notifications`, `admin`, `errors`, `theme`, `language`.

Naming rules:

* keys are `camelCase` leaves: `jobs.title`, `accounts.emptyHint`, `admin.rawHint`;
* API failures follow one pattern per namespace: `error_<code>` where `<code>` is
  the API code (`auth.error_invalid`, `accounts.error_denied`), so a new server
  code needs exactly one key per namespace;
* counts are written `{count} job(s)` or with an explicit unit (`jobs.everyMinutes`
  → `Every {count} min`); vue-i18n pluralisation is **not** used, so a translation
  never has to guess a plural rule for an unknown language;
* interpolation is named: `{count}`, `{provider}`, `{path}` — never positional;
* **no literal UI text in a component**: everything goes through `t('…')`.

## 2. Resolving the language

`initLocale` is called twice by `web/src/main.ts` — once before the first paint
and once more when the session arrives:

```text
1. localStorage['sync.locale']        the operator's own choice (the switcher)
2. session.defaults.default_locale    the administrator's DEFAULT_LOCALE
3. navigator.languages (aliases)      the browser preference
4. en-US                              the fallback
```

Only step 1 is **persisted**: a detected value (or the server default) is applied
without writing `localStorage`. This is deliberate — the first call happens
before the session is known, and writing the browser guess there would look like
an operator choice, so the administrator default could never take effect on the
next load. The switcher (`LanguageSwitcher.vue`) calls `setLocale`, which stores
the choice and mirrors `<html lang dir>`.

The server keeps the same list in `config.SupportedLocales`
([configuration.md](configuration.md)) and `PUT /api/settings` validates against
it, so a settings value can never name a catalog the SPA does not have.

## 3. Right-to-left (`ar-SA`)

* `applyDocumentLocale` sets `<html lang="ar-SA" dir="rtl">`;
* `isRTL(code)` reads the `dir` field of the `LOCALES` descriptor;
* Tailwind's `rtl:` variant keys off that attribute, so spacing/borders that must
  mirror use `rtl:…` utilities rather than `left/right` classes;
* the pre-paint script in `index.html` only touches the theme class, never
  `dir`, so a reload in Arabic never flashes a mirrored layout;
* icons that carry a direction (arrows, chevrons) are chosen per locale, not
  flipped with `transform: scaleX(-1)`.

Verification recipe (headless):

```bash
curl -s -X PUT -H 'Content-Type: application/json' \
  -d '{"default_locale":"ar-SA","default_theme":"dark","sync_default_interval_minutes":60,"sync_run_timeout_minutes":30}' \
  http://127.0.0.1:3000/api/settings
# then load / in a fresh browser profile and check <html lang dir>
```

With `ar-SA` the document must report `lang="ar-SA"` and `dir="rtl"`, and the
navigation must render Arabic labels (لوحة التحكم …). Restore `en-US` afterwards.

## 4. Numbers, dates and sizes

Every value the UI renders goes through `web/src/lib/format.ts`, so the format
follows the active locale (`Intl` handles the RTL digits and the separators):

| Helper | Use |
|---|---|
| `formatBytes(bytes, locale)` | file sizes (`1,5 Mo` vs `1.5 MB`) |
| `formatDateTime(value, locale)` | timestamps (`dateStyle: medium`, `timeStyle: short`) |
| `formatDate(value, locale)` | dates without time |
| `formatRelative(value, locale)` | "in 5 minutes", "2 hours ago" (`Intl.RelativeTimeFormat`) |
| `formatDuration(ms, t)` | run durations, translated (`common.durationMinutes`) |
| `formatNumber(value, locale)` | plain counts with locale grouping |

A component that hand-rolls a date or a byte count is a bug: the locale switch
would not affect it.

## 5. Server errors

The API answers a machine-readable `code` plus an English `error` message
([api.md](api.md)). The SPA reads them with `codeOf(error)` / `messageOf(error)`
(`web/src/lib/api.ts`), looks up `namespace.error_<code>` and falls back to
`namespace.error_unknown` when a code has no key yet:

```ts
const key = `accounts.error_${codeOf(error)}`;
failure.value = { code: codeOf(error), detail: messageOf(error) };
```

Conventions worth keeping:

* one `error_<code>` per namespace that surfaces the failure (accounts, auth,
  jobs, notifications, admin) — a new server code fails the parity check until
  all seven catalogs carry it;
* the English `error` string is shown as *technical detail* (never translated);
* a code with a better-wording alias gets one in the view (`LoginView.vue` maps
  `unauthorized` → `error_invalid`, because on the login form that code means
  "wrong credentials", not "session expired").

## 6. Parity checker

```bash
cd web && node scripts/check-i18n.mjs   # or: npm run typecheck
```

It fails when a catalog misses a key, defines an unknown one, leaves a value
empty, still holds a `TODO`, loses a `{placeholder}`, or when a component uses a
key no catalog defines. Output of a healthy tree:

```text
check-i18n: ok — 7 catalogs × 513 keys, 345 keys referenced from src/, 168 referenced only dynamically (…)
```

("referenced only dynamically" are keys built at runtime, e.g.
`t('nav.' + item.name)` and the `error_<code>` families.)

## 7. Adding a locale

1. `web/src/i18n/locales/<code>.json` — copy `en-US.json` and translate the
   values (never the keys).
2. `web/src/i18n/index.ts` — import it, add it to `MESSAGES`, and add a
   `LOCALES` descriptor (`{code, label, dir}` with the native name).
3. `internal/config/config.go` — add the code to `SupportedLocales` (the settings
   form and `Admin > Settings` validation read it).
4. If browsers spell the language differently, extend `ALIASES`.
5. `node scripts/check-i18n.mjs` and `npm run build`; then verify a render (see
   the recipe in §3).
6. Update this file, `docs/architecture.md` and the language count in
   `docs/branding.md` if the asset copy mentions it.
